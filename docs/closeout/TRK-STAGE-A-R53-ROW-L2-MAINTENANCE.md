## What was built (reuse only)
- `stage_a/tracker/row_maintenance.py`: `RowBinding`, `verify_stored_rows`, `verify_feature`, `record_row_maintenance`. For each stored row of the feature: re-read the row (bytes re-hashed, independent hash recomputed), its predecessor and inputs, re-run the existing independent `verify_row_step` through the SUPPLIED profile port (the same port the separated row handlers use), and require the re-derived result hash to equal the evidence hash the ACCEPTED record carries.
- Outcomes: VERIFIED; FAIL (verifier FAIL, unreadable/corrupt stored row or predecessor, evidence differs from acceptance, unattributable sidecar); UNAVAILABLE (inputs not re-readable, profile/ports/schema/invariant identity unbound, zero accepted rows, accepted manifest unreadable). Never PASS on absence; `l1_fallback` stays False.
- Attribution of stored rows to the feature is by the ACCEPTED manifest hash + version (subject-bound). No symbol↔byte-id equality is guessed. A sidecar that cannot be parsed cannot be attributed and fails closed for every row-maintained feature (disclosed blast radius); a corrupt row of another feature does not fail this one (tested).
- Stored rows with no ROW_ACCEPTED record are listed PENDING and not counted. Original accepted records and stored rows are untouched; current trust is recorded only in the Core (tested: journal heads and row bytes identical before/after).
- `Composition.register_row_maintenance(result, profile)` (only for a result this Composition published) and `run_stored_value_pass` dispatch (existing bounded pass; no cadence, calendar, new Health kind or byte format). When the feature also has a feature-version `StoredBinding`, rows and segments are combined WORST-OF in ONE Core record (the Core holds one health slot per subject, so a later PASS must not mask a FAIL).
